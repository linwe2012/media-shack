# FFmpeg Queue — implementation guide for Gemini

This document is a design handoff for discussion with Gemini Neon. Implementation begins only on a separate request.

The planned product is a local desktop app for Windows and macOS. A user should be able to drop a folder of videos, choose **Archive → Balanced**, see where the files will go, click **Start queue**, and come back the next morning to a useful account of what finished and what needs attention. Keep originals by default. Source cleanup is a separate, explicitly authorized operation after successful delivery. The eventual deliverables are the desktop app, native build instructions and platform test results.

## Desktop stack and build budget

Use Tauri 2, Rust and a static HTML/CSS/JavaScript frontend. Use the system webview (WebView2 on Windows, WKWebView on macOS), native file dialogs, system fonts and vector icons. A single-window queue needs little frontend machinery. Serve local assets directly through Tauri, enable only the necessary IPC capabilities, and use the Cargo Tauri CLI so contributors can build without Node. Rust owns the queue and child processes even when the window is minimized. No server or account is needed. [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) · [Tauri size guidance](https://v2.tauri.app/concept/size/)

Use separately installed FFmpeg and ffprobe for the first release. This keeps codecs out of the app build and lets the user update them independently. On first launch, discover the pair in a configured tools directory, installed locations (including both Homebrew prefixes), then trusted PATH directories. Skip the current working directory. Offer **Locate FFmpeg tools** and persist absolute paths. GUI launches can have a different PATH from terminal launches. Show detected paths, versions, available presets and a short repair action. Only require the encoder selected by a job. A release bundling tools later needs per-platform binaries, provenance, license notices and review of the actual build configuration, including libx265. [FFmpeg build licensing](https://www.ffmpeg.org/general.html#x265)

Proposed initial targets are Windows 11 x64 and macOS arm64 and x86_64. Build on native platform runners and verify both Mac architectures before advertising support. Pin Rust, the Tauri CLI and Cargo.lock. Document a clean-machine recipe per OS covering Xcode command-line tools on Mac, MSVC C++ Build Tools and WebView2 on Windows, installing the pinned CLI, locating the media tools, then running `cargo tauri dev` or `cargo tauri build` from the project root. Package DMG and NSIS installers. For public releases sign Windows binaries and sign and notarize macOS builds. Publish measured clean and incremental build times, installer size, external tool size and idle memory separately. The native toolchain still has a substantial first install. [Tauri build prerequisites](https://v2.tauri.app/start/prerequisites/) · [Distribution](https://v2.tauri.app/distribute/)

## Presets and user controls

Start with the following versioned product defaults. MKV is the default for every Archive combination. Users can select MP4 independently. Best and Balanced are high-quality **lossy** copies. Keeping the original file preserves the original bitstream and metadata.

| Family | Variant | Video encoder | Quality | Encoding effort |
| --- | --- | --- | --- | --- |
| Archive | Best | HEVC, libx265 | CRF 17 | slower |
| Archive | Balanced (default) | HEVC, libx265 | CRF 20 | slow |
| Archive | Best | AV1, libsvtav1 | CRF 22 | preset 3 |
| Archive | Balanced | AV1, libsvtav1 | CRF 27 | preset 5 |
| Remux | Keep encoded streams | stream copy | original | none |

Default to HEVC for the first run. If unavailable, offer an installed alternative and show its settings before enqueueing. CRF sets the encoder's quality target. A lower value generally yields higher quality and larger files within one encoder. Effort changes how much work the encoder spends on compression. No fixed output size, completion time or cross-codec CRF equivalence is implied. Calibrate these proposed defaults on short grainy, dark, fast-motion and animated clips. Record visual observations, bytes and elapsed time with encoder version and hardware. [x265 presets](https://x265.readthedocs.io/en/stable/presets.html) · [SVT-AV1 guide](https://gitlab.com/AOMediaCodec/SVT-AV1/-/blob/cd6567a1ae441ffea43564dd6d1bd7eebfe0c486/Docs/Ffmpeg.md)

Expose family, variant, codec and container in the main settings. Expand **Advanced** for CRF, effort and saving a named preset. For v1, offer tested subsets such as HEVC medium/slow/slower/veryslow and AV1 3–7, plus numeric CRF within each encoder's supported range. Changing codec loads that codec's defaults. Show a Custom indicator after an override and offer Reset. Remux hides encode controls. Store resolved settings with each job at enqueue time. Editing a preset affects future jobs. Allow explicit application to selected pending jobs, followed by fresh preflight. Keep process priority as a queue setting initialized from the selected profile.

## Reusable workflow profiles

A preset describes the encode. A named profile captures the whole batch configuration. For example, **Overnight archive** could select Archive Balanced, HEVC/MKV, background priority, recursive import, a destination root, keep-awake enabled, continue on individual errors and review originals in the morning. Provide Save as profile, Update, Rename, Duplicate and Delete profile. Duplicating a profile creates a settings record. Deleting a profile removes it from the picker. Existing queues retain their saved settings, jobs and history and can select another profile.

### Each tab represents an independent queue

Open one queue tab on first launch. **New queue** creates another empty, independently named tab. Put a profile picker inside each tab. For example, **Family videos** and **Travel footage** can both select **Overnight archive**. Give every queue a stable queue ID. Store its name, tab order, selected profile reference and resolved settings separately from the profile record. Allow many queues to reference the same profile. Key job membership, ordering, run/pause state and history by queue ID. Restore the tabs and selected queue on relaunch.

Selecting a profile supplies defaults for future batches in that queue. Show the active settings when appending to a running batch. Snapshot the resolved settings for each batch and job. Applying changed settings to existing pending jobs requires an explicit action in the target queue, fresh preflight and fresh cleanup consent where applicable. Running jobs finish with their recorded settings.

Drop files or whole folders onto the visible queue. Capture the queue ID and settings snapshot at drop time so switching tabs or changing profiles during a scan cannot redirect or reconfigure the import. Show the queue name, profile and destination in staging. Add Files and Add Folder use the same path. A folder drop imports its videos once, with the existing subfolder toggle.

Start, pause, reorder and retry apply to the selected queue. Use one encoder across all tabs by default. When several queues have been started, finish the current file and rotate among runnable queues one file at a time. Keep duplicate-import checks local to each queue. Coordinate destination reservations and source cleanup across all queues, including queues using the same profile. Bind cleanup consent to the queue, batch and approved source jobs.

Acceptance test: create two named queues using the same saved profile. Drop a folder onto the first, switch tabs during scanning and add files to the second. Pause one while the other runs, change the second queue's profile, then restart. Verify independent membership, settings, order, progress history and pause states. Delete the shared profile and verify both queues survive. Include one source queued in both tabs to exercise cleanup protection.

## Failure policy and morning review

Default to **Continue on individual errors**. Offer **Pause on first error** as a profile option. Record the failed stage, concise cause, affected path and last diagnostic lines. Retry selected failed encodes with fresh preflight. A corrupt input, unsupported track or verification failure leaves its source in place. A full or disconnected destination blocks jobs using that volume until rechecked. Independent jobs can proceed. A missing executable blocks jobs requiring it. Keep failed attempts out of the ready list until retry so a single bad file cannot loop overnight.

Track encode outcome and source cleanup outcome separately. A verified output stays Completed if cleanup is skipped, declined or fails. Offer **Review originals** in the completion summary with original and output sizes, paths, verification results and estimated space recoverable on each source volume. Refresh actual free space after an action. Moving a file to Trash can leave its blocks allocated until the user empties Trash. Budget enough working space for the current source and its output to coexist. If the drive fills mid-encode, stop that attempt safely and offer another destination or a later retry.

### Disk space and minimum savings

- Give each destination volume a configurable free-space reserve. Show current free space and reserve together before Start. Check at admission, periodically during encoding and before finalization. If an active encode crosses the reserve, stop and reap that attempt, remove its positively identified partial and block jobs targeting that volume. Offer **Change destination** or **Retry after freeing space**. Keep other volumes eligible. A reserve is a best-effort margin because other processes can write concurrently.
- Offer an optional profile setting **Minimum size reduction**, off by default. For a user-selected 15% threshold, a 10 GB source qualifies at 8.5 GB or smaller. Evaluate actual whole-file sizes after successful verification and before publication. If the threshold is missed, record **Below savings target · original kept**, record both sizes, discard only the app-owned staged output and continue. Explain this behavior when enabling the setting. Exclude these attempts from published-output and cleanup totals. Never reject a job on a sample estimate.
- During staging, allow sorting by input size or bitrate. Show the current codec and keep inclusion under user control. Already-encoded HEVC or AV1 footage can vary widely in bitrate and quality.
- Acceptance checks include crossing the reserve halfway through a job, two tabs sharing a volume, a second destination with ample space, an exact threshold match, an output larger than its source and restarting after a below-target decision.

## Source cleanup contract

1. **Keep originals** is the default, including for upgraded settings. Profiles may save **Review after completion** or a preference for **Move verified originals to Trash after each file**. A saved preference alone gives no authority to remove files. For unattended trashing, show a batch-start confirmation with the exact source list, item count, total size and destination; default the dialog to Keep. Bind consent to those source identities and recipes. Files added later require their own approval. Review mode starts with no items selected.
2. Use the operating system's recoverable Trash or Recycle Bin operation only. Verify support for the specific volume and require recoverable-only behavior. If that guarantee is unavailable, keep the source and report why. The app never empties Trash or permanently deletes source files. The user controls permanent removal through the OS after inspecting the results.
3. Make eligibility a backend decision shared by manual and unattended cleanup. Require a full-length job, successful source read and encode, complete stream/timing checks, full A/V decode of the output, durable publication and a committed completion record. A preview, partial, canceled attempt or failed verification is always ineligible. Show the lossy codec and any approved conversions in review. Exclude jobs with omitted tracks or known metadata loss from automatic cleanup. Offer **Open output** before a manual decision.
4. Bind the cleanup candidate to the exact regular input file and the exact verified output, using stable volume/file IDs and fingerprints. Immediately recheck both, including output presence and unchanged content, under the cleanup operation. Exclude symlinks, reparse points, ambiguous hard links, paths with replaced ancestors, changed/remounted volumes, source/output aliases and files with unsupported identity checks. Use a platform adapter that prevents path substitution between the identity check and the move. If the adapter cannot guarantee this on a filesystem, leave the original for manual handling outside the app.
5. Serialize cleanup with enqueue and retry decisions. Hold the source while any other job references it and still needs it, including failed or interrupted jobs that can be retried. Require a fresh review when multiple jobs for one source have conflicting cleanup policies. Store an intent with a unique action ID before calling the OS, then record the outcome. If the app crashes across that boundary, reconcile on restart and surface uncertain outcomes for review. Never replay an ambiguous move by pathname. Canceling cleanup or encountering an error leaves the verified output intact and permits unrelated encodes to proceed.
6. Test cleanup against disposable fixtures on both platforms. Cover default keep, confirmed trash, denied or unavailable Trash, output removed or replaced after verification, swapped source path, added jobs after consent, two jobs sharing a source, failed full decode, interrupted publication, and crashes immediately before and after the OS move. Confirm that every ineligible original survives, the intended item is recoverable in the successful case, and no action targets a directory, sidecar, sibling or output. Keep automatic cleanup disabled on any platform or volume type until these checks pass.

## Window and overnight workflow

- Toolbar actions are **Add files**, **Add folder** and **Start queue**. Drag and drop uses the same import path. Folder import includes subfolders by default, with a visible toggle. Stage additions until the user confirms preset, destination, count and any conflicts. Show source-relative names so identically named files are distinguishable.
- Give most of the window to the queue. Each row shows filename, preset/codec, state and progress. Put the selected item's tracks, output path, editable pending settings and error details in a side panel that collapses at narrow widths. Keep diagnostics and the printable command behind **Details**. Use accessible text labels, visible keyboard focus, system light/dark colors and scalable layout. Test Retina and Windows 100%, 150% and 200%, including moving a window between displays.
- Start one encode at a time across the app. Allow reorder, remove pending items, retry selected failures and **Pause after current file**. **Cancel current file** stops that attempt and the next eligible file continues unless the queue is paused. Show elapsed time, speed and ETA when available. End with completed, failed and needs-attention counts and **Show output**.
- Offer **Keep computer awake while working** (default on for an active batch). Acquire an idle-system-sleep assertion while work runs and release on pause, completion, cancellation or error. Allow display sleep. Use an IOKit power assertion on macOS and a dedicated thread managing SetThreadExecutionState on Windows. Manual sleep, shutdown and laptop lid policies can interrupt a run. Recheck volumes and source identity after wake. Closing during work offers **Keep running** (minimize) or **Stop and quit** (save pending items). Start manually in v1. An overnight run requires only the app and a logged-in session.

### The first drop, the overnight run and the morning review

- Open directly to an empty queue with **Drop videos or a folder here**, native pickers, Archive Balanced and Keep originals selected. Creating a profile or naming the queue is optional.
- Beside Start, show the destination, original-file policy and counts such as **18 ready · 2 need review**. Selecting the review count filters to those rows. **Start 18 ready files** runs the eligible items. Keep the review items queued for a decision.
- Show the reason for waiting on the tab or selected job, such as **Waiting for Family Videos to finish its current file**, **Paused by you** or **Waiting for destination drive**. Use the scheduler's actual blocking reason.
- Put a recovery action beside each fixable error. **Choose destination** shows the revised output path. **Use MKV for this file** previews the new track plan and reruns preflight for that item. Keep the diagnostic log one click away.
- In the profile picker use **Use for new files** and **Apply to 30 waiting files**, with the real affected count. Make **Update saved profile** a separate action.
- In the morning summary show results for completed files, such as **12 GB input → 4 GB output · 67% smaller · originals kept**, with **Show output** and **Review originals**. Calculate the batch percentage from summed bytes. Show destination free space and source cleanup outcomes separately.

### Live progress and expandable media details

Keep filename, status, progress and input file size visible in each queue row. For the active job also show output bytes written, encoding speed and ETA. Let each row expand in place with a keyboard-accessible disclosure button. Use this as the input-information view and reserve the side panel for settings and errors. Switching tabs or collapsing a row must not interrupt collection.

- **Input media.** Cache the ffprobe result during import. Show container, exact bytes, duration and overall bitrate, then list each video, audio and subtitle track with its language and disposition when available. For video include codec, dimensions, frame rate (mark averages for VFR), pixel format, bit depth and color information. For audio include codec, channel layout, sample rate and bitrate. Show unknown fields as an em dash. Expanding a row reads the cached result.
- **Live status.** Parse FFmpeg progress blocks about twice per second, collecting processed media time, speed, FPS and total_size when available. Fall back to the current attempt's staging file size for bytes written. During encoding show processed time / duration and estimated remaining encode time from recent stable speed. Use indeterminate progress for unknown duration. Give verification and finalization their own status. Mark completion only after publication.
- **Compression during encoding.** Always show the measured output size so far. Dividing the full input size by a partial output produces a misleading ratio. Once at least 10% of a known timeline is encoded and media time and byte counts are advancing, optionally show **Est. final ratio**. With fraction f = processed media time / input duration, estimate final output bytes as bytes written / f, then divide input bytes by that estimate. Early scenes, copied tracks and container finalization can skew this estimate. Hide it when measurements are missing or unreliable. Estimates must never govern deletion or free-space decisions.
- **Final compression.** After publication use actual whole-file sizes, including audio, subtitles and container overhead. Display input bytes / output bytes as the compression ratio and 100 × (1 − output bytes / input bytes) as the percentage smaller. For example, 4 GiB → 1 GiB shows **4.00:1 · 75% smaller**. For 1 GiB → 1.25 GiB show **0.80:1 · 25% larger**. Use the term “smaller” for the output comparison even when the original remains on disk. Guard against missing or zero sizes. Persist final sizes and ratio inputs in job history so they survive relaunch and source cleanup.
- **Acceptance.** Test a normal encode, unknown duration, unavailable total_size, a growing output larger than the source, and a canceled encode. Check that a partial file never receives a final ratio, expansion works while encoding, and completed metrics agree with the published file size after restart.

### Encode a 15-second sample before starting

Place **Preview 15 seconds** beside the quality controls. For known durations, initially select a scene about one-quarter of the way in, clamped so a full sample fits when possible. Let the user scrub to a demanding scene or enter a start time. Encode up to 15 seconds of media from that point, clamping to the available duration. Use the actual selected encoder, CRF, effort, resolution, pixel format and container. Show sample-encode progress, measured file size and elapsed encode time. If projecting full-file size or runtime, label the estimate “Based on this scene” and omit it for clips too short or durations too uncertain to support it. Mark the sample stale after settings change. Schedule it in the same single-encoder budget as queued jobs and show when it can run.

Offer Original / Encoded comparison at the same media timestamp, with play/pause, a shared seek control and a 100% view for examining fine details. Use the finalized native-resolution sample for quality inspection. Where embedded playback is unavailable, provide timestamp-matched frames decoded by FFmpeg and **Open sample in default player** for playback. A sample belongs to the app's temporary preview area. It never marks a job complete, grants cleanup eligibility or enters the batch size totals.

### Watch HEVC or AV1 during the real encode

Offer **Live preview** on the active job. The initial design is a silent, scaled view refreshed as frames emerge from the encoder. Show the media timestamp and **Waiting for first encoded frame** during encoder lookahead. A slow encode advances at its own speed. Keep the full-resolution sample available for judging grain, texture and motion.

- **Read the output directly where feasible.** Prototype a separate, read-only preview worker for a growing MKV. Decode recent available pictures, show the decoded presentation timestamp and wait for more data at the current end. Avoid repeatedly scanning the entire file. Reading an early keyframe is only a first test. Measure how closely the monitor can follow an hour-long encode. In a local macOS FFmpeg 8.0.1 test, a second process decoded an early frame during both HEVC and AV1 encodes to MKV and fragmented MP4. Standard MP4 with faststart became readable at finalization. Keep the user's selected archive format. [FFmpeg container documentation](https://ffmpeg.org/ffmpeg-formats.html#Fragmentation)
- **Support ordinary MP4.** Prototype a bounded, optional branch carrying copies of the actual encoded video packets to a separate decoder. Configure the branch when launching the job so the panel can open mid-encode. The archive writer must make progress if the decoder is absent, blocked or has crashed. Drop preview data on overflow and resynchronize at a decodable keyframe with the required codec headers. Benchmark attachment delay with the archive preset's actual keyframe spacing. FFmpeg loopback has already produced JPEG frames for both codecs in a local smoke test. Keep loopback as a comparison prototype since running its decoder inside the writer couples their failure modes. [FFmpeg loopback decoders](https://ffmpeg.org/ffmpeg.html#Loopback-decoders)
- **Display and cost.** Open the monitor on demand. Decode and scale only for the active viewer where possible. Start with a silent view at about two frames per media second, cap wall-clock refreshes, keep only the latest display frame and use binary image transport separate from queue events. Use the archive file's bytes for progress. Hide or close the monitor without touching the encode.
- **Release gate.** For both codecs and both containers on Windows and macOS, open the panel after encoding starts, see advancing timestamps, close it, reopen it and compare monitor images with matching timestamps in the finished output. Stall and kill the preview worker mid-job. Require the archive to complete, pass its normal verification and preserve the original. Measure latency, memory and throughput with monitoring on and off. If a tool build lacks a tested preview path, show that specific limitation and keep the queue usable. The direct-read tests above establish early-frame access only. Long-running playback, worker isolation and Windows behavior remain to be demonstrated.

## Media planning and output contract

1. Probe each local file with ffprobe JSON (`-v error -show_format -show_streams -show_chapters -of json`). Inspect stream types, flags, tags, side data and timing. Treat extensions as import hints. Skip symlink directories, destination trees and app-owned partials. Deduplicate by file identity plus resolved recipe and destination. Scan incrementally, support cancelling discovery and report unreadable entries.
2. Pick a destination root on first use. Mirror relative subdirectories for folder imports and propose names such as `Trip/day1.walk.archive-balanced.hevc.mkv`. Preserve the stem including internal dots. Resolve overlapping imports, case-insensitive collisions, pre-existing outputs, reserved Windows names and path limits during staging. Default to a numbered free name. Never replace an existing file or write through an alias of the input.
3. Build an explicit plan for **every** input stream. Encode the main moving video and copy compatible audio, subtitles, attachments and covers. Preserve chapters, language, titles, default/forced dispositions, aspect ratio, orientation, frame timing and color properties where supported. Treat attached pictures separately from moving video. Block ambiguous multi-angle or multiple real video streams in v1 until the user chooses a supported plan. Show any proposed conversion or omission by track before starting. For MP4 with ASS styling, bitmap subtitles, fonts or incompatible audio, offer MKV first. Require explicit opt-in for a supported fallback such as audio to AAC or simple text to mov_text, showing what changes. Keep unresolved items in Needs attention and continue eligible jobs.
4. First certify progressive SDR 8/10-bit 4:2:0 for encoding. Preserve bit depth and chroma using an explicitly supported pixel format. Handle VFR with passthrough timing and test timestamps. Disable automatic rotation during encode if preserving rotation metadata, and verify displayed orientation. For interlaced video, HDR10/HLG, Dolby Vision, HDR10+, alpha, unusual chroma or uncertain side data, gate encoding on a verified preservation path. Offer compatible stream-copy remux or retain the source. Do not silently tone-map, deinterlace, downsample, synthesize grain, rescale or flatten multiple tracks.
5. In Rust assemble an argument vector, preserving native paths. Launch the selected local binary directly. Restrict imports to supported local media and block network protocols and playlist/manifest inputs in both probe and encode paths. Run a capability check with versions, muxers, encoder help and tiny encode/mux smoke tests. Cache by tool identity and invalidate when tools change. Preflight each source, including writable destination and free space. CRF size estimates are uncertain. Monitor free space during the run and pause remaining work on a volume-wide error.

Example argv for the simple case of one SDR 8-bit moving video at stream 0 and compatible audio at stream 1. Paths are individual arguments. Generalize from the probed plan, including per-stream metadata and dispositions. Use the actual selected muxer despite the temporary suffix. [FFmpeg stream selection and progress](https://www.ffmpeg.org/ffmpeg.html)

```text
["-hide_banner", "-n", "-xerror", "-nostats", "-progress", "pipe:1",
 "-protocol_whitelist", "file,pipe", "-noautorotate", "-i", INPUT,
 "-map", "0:0", "-map", "0:1", "-map_metadata", "0", "-map_chapters", "0",
 "-c", "copy", "-c:v:0", "libx265", "-preset:v:0", "slow", "-crf:v:0", "20",
 "-pix_fmt:v:0", "yuv420p", "-fps_mode:v:0", "passthrough",
 "-f", "matroska", UNIQUE_PARTIAL]
```

For AV1 substitute libsvtav1 and its numeric preset and CRF. For MP4 use the mp4 muxer, test HEVC hvc1 signaling with target players, and enable faststart when writing a seekable file. Keep the UI in Finalizing while the muxer finishes. Remux uses explicit maps and stream copy.

## Queue engine, recovery and platform behavior

Keep a pure Rust planner (probe + recipe → stream plan + argv), a process runner, an SQLite store, and small platform modules for priority, child lifetime, power and exclusive file publication. Keep the Tauri command surface typed and narrow: import, inspect, update pending, reorder, start, pause-after-current, cancel, retry and reveal. Send compact progress events. On window reload fetch a full queue snapshot.

Persist queue order and pause state plus job ID, source path and fingerprint (identity, size, mtime), tool versions, preset snapshot and schema version, track decisions, destination, attempt ID, temporary path, status and last error. Store SQLite in per-user app data. Apply transactional migrations and use a single scheduler with an OS-level instance lock. Record an attempt before launch. Keep statuses visible as Queued → Probing → Ready → Encoding → Verifying → Publishing → Completed, with a terminal Below savings target branch from Verifying before publication and Needs attention, Failed, Canceled and Interrupted branches. Pause gates admission to Encoding. Retry starts a fresh attempt at the beginning of the file.

- Set priority on the FFmpeg child. Offer Background (default), Below normal and Normal. Map on Windows to IDLE, BELOW_NORMAL and NORMAL priority classes; use nice increments of 10, 5 and 0 on macOS relative to normal launch priority. Apply changes at the next job boundary and display that behavior. Report failure to set priority. Priority lets interactive work run first; a background encode can still use all otherwise idle cores.
- Drain stdout progress and stderr concurrently. Parse progress blocks and out_time_us, use probed duration for a bounded estimate, and show indeterminate progress for unknown durations. Keep logs bounded per attempt. An FFmpeg progress=end message alone cannot mark a job complete. Check exit status, cancellation state and verification.
- Give each attempt a private staging directory on the destination volume and a unique file inside it. Gracefully stop via FFmpeg's piped stdin, wait briefly, then terminate and reap the owned child tree. Use a Windows Job Object with kill-on-close. On macOS use a child process group and a supervisor that detects parent loss via pipe EOF and reaps its group. Test forced app termination on both platforms. Never kill a reused PID on restart.
- After a clean exit, probe the staged output and compare the planned streams, codecs, track flags, chapters, dimensions, pixel format, timing and duration. Derive timing tolerance from input time bases and permitted codec delay. Missing duration requires a separate completeness check such as decoded frame count against source. With Keep originals, default to structural and completeness checks and offer a full A/V decode as an option. Require a full decode before any source cleanup, including a later manual cleanup through the app. Keep incomplete or failed outputs out of the final namespace.
- Persist a publishing intent with staged file identity, size and final path. Flush and use an OS-supported same-volume atomic no-replace operation. Commit Completed only after publication. If another program creates the destination, choose a new free name and update the intent before retrying. On launch reconcile Publishing against the recorded identity to handle a crash between publication and database commit. If identity or filesystem guarantees are uncertain, leave the job in Needs attention. Reconcile other stale active attempts as Interrupted; preserve pending order and offer Resume queue. Only clean up positively identified app-owned staging files after child exit.
- Classify source-specific failures separately from shared failures. A corrupt file must not stop the next movie. A missing tool or full destination should pause affected work and show one actionable reason. Disconnecting a removable disk must not redirect output to a local folder mounted at the same path. Recheck volume identity, available space and source fingerprint before retry or publication.

## Unified Platform Extension (Specification v1.0)

Building on the verified batch encoder/remuxer above, MediaShack is extended into a unified local-first media management and archival platform while preserving every existing queue, preset, profile, preview, verification, and source-cleanup guarantee:

- **Architecture Decision Record**: See [ADR.md](ADR.md) and full specification in [PLAN_SPECIFICATION.md](PLAN_SPECIFICATION.md).
- **Core Principle**: *Scan once, cache everything, and reuse analysis across features.*
- **Unified Catalog (`src-tauri/src/catalog.rs`, `db.rs`)**: Persistent SQLite catalog (migrations `v3+`, WAL, FTS5) separating logical `media_assets`, physical `media_files`, `file_locations`, `volumes`, and `media_relationships`, supporting lazy analysis levels 0–5, offline drives, hard links, Unicode/long paths, and external renames/moves.
- **Organization (`src-tauri/src/organize.rs`)**: Namespaced/hierarchical tags with provenance, aliases, merging, AND/OR/NOT search, virtual collections, template-based batch rename (with regex, collision/reserved-name checks, cycle safety), and journaled batch move/copy with cross-volume copy-verify-commit and undo.
- **Duplicate & Similarity (`src-tauri/src/duplicates.rs`)**: Exact duplicates (size -> partial -> BLAKE3 + SHA-256), encoded-stream equivalence, perceptual video hashing (pHash/dHash/DCT) with LSH/duration candidate indexing, temporal overlap alignment (offset voting / DTW) for trimmed/partial clips, and side-by-side quality comparison.
- **Metadata Interoperability (`src-tauri/src/metadata_interop.rs`)**: Optional Windows Property System (`System.Keywords` / `IPropertyStore`), macOS Finder tags, ExifTool / lossless FFmpeg embedded metadata, JSON/XMP sidecars, and explicit conflict resolution.
- **Shared Analysis, Integrity, Repair, Tasks (`src-tauri/src/analysis.rs`, `integrity.rs`, `repair.rs`, `tasks.rs`)**: Shared adaptive FFmpeg frame sampler (including VR180/VR360 single-eye handling), bounded artifact cache, black/frozen-frame detection, BLAKE3/SHA-256 archival manifests, MP4 atom diagnosis & lossless/reference recovery, and resource-aware task scheduler (HDD/SSD aware, throttling analysis during transcoding).
- **Intelligence Features (`src-tauri/src/intelligence.rs`)**: Local Chinese/English OCR & persistent watermark vs subtitle detection, optional semantic search (CLIP/SigLIP + local feature fallback, media & timestamp level), opt-in local anonymous face grouping with biometric purge, and optional Ollama/LM Studio/OpenAI-compatible structured rule generation (previewed before execution).
